# 4 План тестирования

## 4.1 Объект и стратегия

Объект проверки — версия 1.0.0: интерфейс, HTTP API, бизнес-правила, PostgreSQL и операции резервного копирования. Основной подход — функциональные интеграционные тесты через HTTP на реально работающих контейнерах. Дополнительно выполняются прямые проверки ограничений SQL, ручные проверки в браузере и восстановление копии в изолированную базу.

Автоматический набор содержит 46 именованных сценариев TC01–TC46. Параметризация входа по ролям, проверки объемов, CRUD нескольких сущностей и шести отчетов расширяет их до 64 проверок. Это превышает минимум 30 Test Cases. Начальные условия: тестовый DML, работающие db и web, учетные записи с демонстрационным паролем. Набор следует выполнять на учебном стенде, поскольку он временно создает и удаляет тестовые записи.

Перед прогоном: проверить /health; убедиться, что тестовые данные не изменены; сохранить необходимую копию. После прогона: проверить количество записей, XML-результат и отсутствие неубранных тестовых сущностей. Тесты CRUD удаляют созданные записи, а SQL-проверки откатывают неуспешные транзакции. События журнала и счетчики последовательностей закономерно остаются измененными.

## 4.5 Критерии завершения тестирования

Обязательные серверные сценарии должны завершиться успешно. Ошибка, позволяющая прочитать чужие оценки, обойти вход или сохранить некорректную связь, блокирует приемку. Ошибки расчета и экспорта также блокируют приемку до исправления. Ручные пункты, не выполненные при подготовке, остаются явно отмеченными; их нельзя считать пройденными по наличию соответствующего кода.
