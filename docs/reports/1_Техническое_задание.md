# 1 Техническое задание

## 1.1 Общие сведения о проекте

Полное наименование: информационная система «Учет успеваемости студентов». Краткое наименование: ИСУУ. Версия учебной реализации — 1.0.0. Заказчик в рамках предметной области — деканат университета. Пользователи — администратор, сотрудники деканата, преподаватели и студенты. Имена исполнителей и реквизиты образовательной организации заполняются на титульном листе.

Система предназначена для ведения учебных данных в рамках одного университета. Рабочая единица учебного процесса — назначение дисциплины группе на семестр конкретного учебного года с ответственным преподавателем. Внутри назначения создаются контрольные работы, по которым вводятся оценки студентов этой группы.

## 1.2 Цели и задачи

Цель — исключить ручное сведение журналов и повторный расчет показателей в электронных таблицах. Для достижения цели требуется централизовать справочники, обеспечить проверку вводимых значений, разделить права пользователей и получать ведомости из единого источника данных.

Задачи: проанализировать предметную область; зафиксировать требования; построить ER и Use Case модели; создать физическую базу и тестовый набор; реализовать интерфейс, бизнес-логику и экспорт; провести проверки; подготовить инструкции по установке, эксплуатации и восстановлению.

## 1.3 Исходные проблемы и границы автоматизации

При хранении данных в бумажных журналах и независимых таблицах одна группа или дисциплина может иметь несколько написаний. Оценки приходится переносить между документами вручную, средний балл пересчитывать, а сводную ведомость собирать за несколько семестров. Централизованные справочники и внешние ключи устраняют разрыв между связанными записями; единое представление results обеспечивает одинаковую основу отчетов.

В учебный объем не включены интеграция с государственными системами, электронная подпись, расписание занятий, учет посещаемости и очередь фоновых заданий. Экспорт небольших отчетов выполняется синхронно, поэтому RabbitMQ не требуется. Организационная защита проекта и размещение на учебном портале выполняются участниками команды.

CRUD означает создание, чтение, изменение и удаление. Полномочия проверяются на сервере при каждом запросе. Скрытие кнопок в браузере служит удобству интерфейса и не является единственным средством защиты. Студент получает только собственную строку рейтинга, вычисленную относительно всей своей группы. Имена и оценки остальных студентов ему не передаются.

Преподаватель видит списки студентов только тех групп, которым назначены его дисциплины. Редактирование работы или оценки требует проверки исходного и нового назначения. Это предотвращает изменение чужой записи через подстановку идентификатора. Деканат ведет справочники и назначения; ввод оценок принадлежит преподавателю и администратору.

## 1.6 Правила расчета оценок и отчетов

Для балльной работы допустимы целые значения 2, 3, 4 и 5. Значения 0 и 1 используются исключительно для незачета и зачета. Такая интерпретация пятибалльной шкалы принята для университетской аттестации: минимальная выставляемая оценка — 2. Шкала каждой работы должна соответствовать форме контроля дисциплины. Положительный вес работы находится в интервале (0; 100].

Итог по балльной дисциплине рассчитывается по формуле (1), только если оценки введены по всем ее работам. Сумма весов не обязана равняться единице или ста: выполняется нормирование на общую сумму. Для зачета итог равен 1, когда все работы сданы; любой незачет дает 0. Отсутствие работ или хотя бы одной оценки дает пустой итог и признак «Не завершено».

```
Итог = round(Σ(оценкаᵢ × весᵢ) / Σвесᵢ)                         (1)
```

Округление выполняется PostgreSQL для numeric до целого: дробная часть 0,5 округляется вверх для положительных оценок. Пример: оценки 5, 3, 4, 5 при весах 1, 2, 2, 5 дают (5 + 6 + 8 + 25) / 10 = 4,4; итог — 4. Работа «Итог семестра» является одним из компонентов, а не ручной заменой рассчитанного результата.

Средний балл студента — арифметическое среднее завершенных балльных итогов дисциплин, округленное до двух знаков. Зачеты и незавершенные итоги исключаются. При отсутствии завершенных балльных дисциплин показатель остается пустым. Рейтинг сортируется по среднему баллу по убыванию; одинаковым значениям соответствует одинаковое место, следующее место увеличивается на единицу (dense_rank).

Отчет по должникам включает завершенные неудовлетворительные результаты: 2 для балльной дисциплины и 0 для зачета. Отсутствующие оценки показаны в ведомостях как незавершенные, но автоматически не объявляются задолженностью. Статистика строится отдельными срезами по группам, курсам и специальностям. Успеваемость — отношение числа положительных завершенных итогов к общему числу завершенных итогов.

```
Успеваемость = 100 × положительные итоги / завершенные итоги       (2)
```

Качество знаний определяется по студентам, имеющим назначения в выбранном срезе. В числитель входят студенты, у которых все балльные итоги равны 4 или 5, все зачеты сданы и нет незавершенных назначений. Необходимо наличие хотя бы одной балльной дисциплины. Знаменатель — число студентов с назначениями в этом же срезе. При фильтрации по отдельному назначению качество относится только к выбранной дисциплине.

```
Качество = 100 × студенты с результатами 4/5 / студенты с назначениями (3)
```

Без фильтров отчеты охватывают все сохраненные назначения, в том числе прошлые периоды и студентов с неактивным учебным статусом. Для проверки конкретного семестра используется назначение, содержащее год и семестр. В интерфейсе групповой фильтр и фильтр назначения применяются совместно. Несовместимые параметры закономерно возвращают пустой отчет.

## 1.7 Надежность и безопасность

Изменение записи и добавление события в журнал выполняются в одной транзакции. Ошибка валидации или ограничения PostgreSQL отменяет операцию. Наличие внешних ключей не позволяет удалить группу со студентами, дисциплину с назначениями или работу с оценками. Изменение группы студента с историей оценок запрещено, чтобы история не оказалась у другой группы.

Пароль хранится как PBKDF2-HMAC-SHA256 с индивидуальной солью и 260000 итерациями. Сессионный токен генерируется криптографическим генератором; в PostgreSQL сохраняется только его SHA-256-хеш. Сессия действует восемь часов, проверяется совместно с активностью учетной записи и удаляется при выходе. Изменение учетной записи отзывает ее сессии.

Cookie имеет HttpOnly и SameSite=Strict. Для локального HTTP Secure отключен; при размещении за HTTPS необходимо включить COOKIE_SECURE=true. Сервер проверяет Origin изменяющих запросов и возвращает заголовки CSP, X-Frame-Options и nosniff. Пользовательские значения передаются в SQL параметрами; таблицы и поля выбираются из белого списка. После десяти неудачных входов для пары IP-адрес и логин следующие попытки блокируются на пятнадцать минут.

Журнал хранит пользователя, действие, сущность, идентификатор записи и время. Пароли и токены в события не включаются. Журнал отображает последние 500 событий, более ранние остаются в базе. Полная резервная копия создается pg_dump в формате custom. Веб-архив является отдельной выгрузкой прикладных данных и не заменяет полноценную резервную копию.

## 1.8 Условия эксплуатации и приемка

Учебный стенд работает на одном компьютере с Docker Engine или Docker Desktop и Docker Compose v2. Рекомендуемый учебный минимум: двухъядерный процессор, 4 ГБ свободной оперативной памяти и 3 ГБ дискового пространства. Это практический ориентир для небольшого набора данных, а не результат нагрузочного испытания. Для первоначальной сборки нужен доступ к реестрам контейнеров и Python-пакетов.

Порт приложения привязан к 127.0.0.1:8000. База данных не публикует порт на хост. Браузер должен поддерживать Fetch API и HTML dialog. Условия приемки: старт обоих контейнеров; требуемый объем DML; CRUD всех прикладных сущностей; правильный расчет контрольных примеров; шесть отчетов; экспорт; отсутствие доступа к чужим данным; успешные проверки и наличие документации.

Перед реальной эксплуатацией необходимы индивидуальные пароли вместо демонстрационных, HTTPS, согласование правил аттестации с вузом, нагрузочная проверка, регламент резервного копирования и правила обработки персональных данных. Учебный протокол не заменяет такие процедуры.
